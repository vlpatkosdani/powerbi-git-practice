# s02 · Create a feature branch

Module 1: Solo basics · self-guided: you prepare the starting point yourself, no automatic check

## Why this matters

If you need to develop something new, modify an existing feature or just try out something separately from your main/prod work, create a new branch. That will be your feature branch. Give it a name that tells others what's inside, for example `feature/margin-measures`.

Why is it important? If everyone works directly on the main branch, that branch is only as good as the last person's half-finished work. With a feature branch your changes stay separate until they are ready, and the main branch always has a model you could deploy. It's also the starting point for everything later: you can't open a PR or cherry-pick a change if it's mixed with everything else.

If the team is comfortable with branching and merging, most of the daily work is covered. These basics will be needed by everyone on day one, so I'd suggest putting extra effort into practising them.

## What it looks like

Create the branch from the shared branch and switch to it in one step:

```
$ git switch -c s02/feature-double-margin main
Switched to a new branch 's02/feature-double-margin'
```

Add the measure in Desktop, save, and look at the diff before you commit:

```diff
         changedProperty = FormatString

+    measure 'Double Margin' = [Margin] * 2
+        formatString: #,0.00
+        lineageTag: 9a1e2b3c-4d5e-4f60-8a7b-1c2d3e4f5a6b
+
     column 'Order Number'
```

The `lineageTag` is generated by Power BI Desktop. Yours will be different, that's fine. The `formatString` is the same as the other margin measures, so the new one looks consistent in the report.

After the commit, `git branch` shows where you are (the `*`) and that `main` didn't move:

```
$ git branch
* s02/feature-double-margin
  main
```

*TMDL is indented with tabs in the real files; it's shown with spaces here. Commit hashes and lineageTags will be different on your machine.*

## Start

Starting point: `main`.

## Steps

1. Create and switch to a new branch called `s02/feature-double-margin`, starting from `main`:

   **VS Code UI:** Click the branch name in the status bar, select `Create new branch from...`, pick `main` and type `s02/feature-double-margin`.

   **Terminal:**
   ```bash
   git switch -c s02/feature-double-margin main
   ```
2. Open `Contoso.pbip` in Power BI Desktop, select the `Sales` table and click `New measure`.
3. Enter the following DAX expression:
   ```dax
   Double Margin = [Margin] * 2
   ```
4. Format it the same way as `Margin` (`Measure tools` > `Format`: decimal number, thousands separator, 2 decimals).
5. Save: `Ctrl+S`.
6. Stage, commit, and push:

   **VS Code UI:** Go to the Source Control panel, stage the changed file with `+`, enter the message `Double margin measure added`, click `Commit`, then `Publish Branch`.

   **Terminal:**
   ```bash
   git add .
   git commit -m "Double margin measure added"
   git push -u origin s02/feature-double-margin
   ```
7. Refresh the repo page on GitHub and open the branch list.

## How to know it worked

- [ ] Your branch is on GitHub
- [ ] On your branch, `Double Margin` is in `Sales` with the `#,0.00` format
- [ ] Switch back to `main` and click `Apply external changes` in Desktop: `Double Margin` isn't there
- [ ] `python tools/check.py s02` says all good (it checks the result for you)

## Tips

> Tip: Use prefixes in your branch names, like `feature/`, `hotfix/`, `bugfix/`, `test/` or `release/`. It's a small habit that pays off quickly:
>
> - **Your branches get organised into folders.** Azure DevOps shows the part before the `/` as a folder, so all `feature/...` branches sit together, all `hotfix/...` branches sit together, and so on. On GitHub and in VS Code you can type `feature/` in the branch search and get only those.
> - **The name tells you what kind of work it is.** `hotfix/total-quantity-sum` says "this is urgent and it starts from PROD" before anyone opens it. `feature/margin-measures` says "new work, goes through the normal flow". `test/new-date-table` says "just trying something, might never be merged".
> - **You can attach rules to a prefix.** Branch protection rules on GitHub and branch policies in Azure DevOps can target a pattern like `release/*`, e.g. "nobody pushes here directly, only through a reviewed PR". A GitHub Actions workflow can run only for `hotfix/**` branches, for example to run BPA on every hotfix before it goes to PROD.
> - **Cleaning up is easier.** After a few months you'll have dozens of branches. `feature/...` branches that are already merged can go. `test/...` branches can go too, once the experiment is over. With prefixes you see at a glance which is which.
> - **Add the ticket number if you have one:** `feature/1234-margin-measures`. Then you can find the branch from the ticket, and the ticket from the branch.
>
> One catch: if a branch called `feature` exists, git won't let you create `feature/margin-measures` (and the other way around), because git stores branch names like folders and files. So use the prefix only as a folder, never as a branch name on its own.
